# 設定分發 POC 決策紀錄

> 這份持續更新的紀錄保存 POC 設計過程中的決策，同時保留目前方向，以及已取代、已延後或已否決的替代方案。它不是最終設計規格。
>
> 紀錄日期：2026-08-27

正式的領域用語定義於 [`CONTEXT.md`](../../CONTEXT.md)。只有當決策難以逆轉、缺乏背景時容易令人困惑，且源於實際取捨，才會提升為 ADR。

## 狀態

- **已接受（Accepted）**：目前 POC 採行的方向。
- **已延後（Deferred）**：不屬於目前 POC，但在重新評估條件成立時值得再次考慮。
- **已取代（Superseded）**：曾經考慮或接受，後來由新的決策取代。
- **已否決（Rejected）**：因違反預期語意或限制而明確排除。

## 決策

### POC-001 — POC 範圍與交付形式

**狀態：** 已接受（Accepted）

本 POC 優先採用 .NET 8，包含三項交付成果：

1. 以 SQLite 作為儲存後端的設定管理 HTTP 服務。
2. 將中央設定載入使用端應用程式（Consumer Application）的 NuGet 套件。
3. 使用該套件的 .NET 8 示範 HTTP 服務，提供 POC-055 定義的優先使用之限定範圍示範介面，以及明確標示不安全的根層級診斷介面。

實作順序先示範 .NET 8 路徑。這不表示 POC 排除 .NET Framework 4.8：後續階段可依 POC-056 加入 Framework Receiver。使用端應用程式透過 HTTP 存取中央設定主機（Central Config Host），無須直接存取其資料庫。代管或商用設定產品不在本 POC 選定的範圍內。

### POC-002 — 共用值的識別方式

**狀態：** 已接受（Accepted）
**ADR:** [`ADR-0001`](../adr/0001-share-value-by-environment-and-key.md)

設定項目（Configuration Entry）由一組中央環境（Environment）與設定鍵（Configuration Key）識別。每個要求同一組中央環境與設定鍵的使用端應用程式，都會取得相同的目前中央值。若預期值不同，就必須使用不同的設定鍵；不會把使用端專屬的值藏在同一個設定鍵之後。

這是只需修改一次共用值，就能免去逐一修改數十個應用程式的核心機制。

### POC-003 — 由使用端擁有的設定鍵選擇

**狀態：** 已接受（Accepted）
**ADR:** [`ADR-0002`](../adr/0002-consumer-owned-key-selection.md)

每個使用端應用程式擁有自己的設定鍵選擇（Key Selection），並傳送實際需要的完整設定鍵清單。設定伺服器不儲存使用端登錄清單，也不要求應用程式在建立或變更設定鍵選擇時進行登錄。

這讓伺服器不必處理使用端的部署問題，代價是 POC 不提供伺服器端的相依性分析或影響分析。

### POC-004 — 以 ConfigSet 為基礎的選擇

**狀態：** 已取代（Superseded），由 POC-003 取代

曾探索將 ConfigSet 設計為一組具名稱的設定鍵。使用端應用程式可選擇一個或多個 ConfigSet，自行持有排序後的清單，並在設定鍵重疊時，允許後面的集合覆寫前面的集合。伺服器仍不會登錄使用端。

本 POC 改以精確的設定鍵選擇取代這個模型，因為尚未證實重複使用的需求，具名群組、重疊順序、未使用的值與集合發布語意就已增加複雜度。

**重新評估條件：** 穩定的設定鍵群組在許多使用端應用程式中反覆出現，且維護精確清單已成為可量測的維運負擔。未來若加入分組，仍應是使用端為方便管理設定鍵選擇而擁有的功能，不應預設引入伺服器擁有的使用端登錄清單。

### POC-005 — ConfigSetRevision 與多個設定鍵的原子發布

**狀態：** 已延後（Deferred）

本 POC 不引入 ConfigSetRevision、發布快照，或橫跨多個設定鍵的原子發布邊界。管理介面每次只寫入一個設定鍵，因此沒有需要識別的多鍵修訂版本。

**重新評估條件：** 一組相關設定鍵必須以一致的發布版本同時切換，而且使用端應用程式絕不能觀察到新舊值混合的結果。

### POC-006 — 批次設定分發讀取

**狀態：** 已接受（Accepted）

使用端應用程式針對一個中央環境，在單一批次要求中傳送精確的設定鍵選擇。套件不得對每個設定鍵各發出一次 HTTP 要求。伺服器回傳目前擁有的值，並指出所選設定鍵中哪些沒有目前中央值。

路由與承載資料定義於 POC-022 與 POC-026。設定鍵比對定義於 POC-028。POC-050 限制每個回傳設定值的大小，POC-052 定義共用的錯誤表示格式，POC-053 則刻意不加入 POC 專屬的批次設定鍵數量或回應總大小限制。

### POC-007 — 僅追加的單一設定鍵寫入

**狀態：** 已接受（Accepted），適用於本 POC

每次管理寫入都針對一組中央環境與設定鍵，插入一個帶有 `CreatedAtUtc` 的新項目版本（Entry Version）。不執行 Upsert 或原地更新。最新的項目版本決定設定項目的目前狀態。

這可保留歷史紀錄，並讓第一版寫入介面保持簡單。項目版本配置定義於 POC-023，嚴格的移除行為定義於 POC-024，單一執行個體的持久化拓撲定義於 POC-041，保留策略定義於 POC-043，交易順序定義於 POC-048，SQLite 競爭處理定義於 POC-049。在 POC 驗證這些持久化語意之前，此決策保留在本紀錄中，不提升為 ADR。

### POC-008 — 空字串與移除語意

**狀態：** 已接受（Accepted）

以空字串執行 `Set` 會建立實際存在的中央值；它既不是缺值，也不是移除（Removal）。移除會插入新的項目版本，使目前中央值不再存在，同時保留歷史紀錄。之後再次執行 `Set`，會插入另一個版本，使該設定鍵重新存在。

在設定分發時，已移除的設定鍵沒有目前中央值，因此視為缺少的設定鍵（Missing Key）。較低優先順序的本機值是否會生效，取決於 POC-010 定義的該設定鍵缺值行為（Missing Behavior）。

已否決實體刪除，以及以空字串表示移除的做法。

### POC-009 — 所有選取設定鍵採用相同的缺值行為

**狀態：** 已取代（Superseded），由 POC-010 取代

設計曾短暫要求：凡是選取的中央設定鍵缺值，都必須使應用程式啟動失敗。這能揭露遺漏，但也會讓移除或遷移期間的缺口中止所有受影響的使用端應用程式，即使本機已有安全的值。

對每個缺少的設定鍵無條件使用後備值，也被認為不安全，因為它會在沒有提醒的情況下重新啟用過時的本機值。這兩種全域策略都已由逐鍵明確選擇的方式取代。

### POC-010 — 依設定鍵決定缺值行為

**狀態：** 已接受（Accepted）

每個選取的設定鍵，都有一種由使用端擁有的缺值行為：

- **中央必要設定鍵（Central-Required Key）**：中央值缺少或已移除時，使啟動失敗。
- **允許後備設定鍵（Fallback-Allowed Key）**：中央值缺少或已移除時，允許其他非中央設定來源決定其有效值。

因此，使用後備值必須明確宣告，且範圍限定到個別設定鍵。它不是中央系統故障時的一般復原機制。若允許後備設定鍵在所有設定來源中都不存在，POC-035 將應用程式層級的必要性判斷交由使用端應用程式負責。

### POC-011 — 中央系統故障時快速失敗（Fail Fast）

**狀態：** 已接受（Accepted）

當設定分發服務無法提供可信賴的回應時，啟動必須失敗，包括逾時、連線失敗、未授權存取、伺服器錯誤或無效回應。這同時適用於中央必要設定鍵與允許後備設定鍵，因為這些分類描述的是有效回應中個別設定鍵缺少的情況，而非中央系統本身無法使用。

POC-038 定義最終失敗前採用的有限重試與逾時策略。POC-039 定義啟動診斷與不洩漏設定值的記錄。POC-040 刻意將身分驗證與授權排除於 POC 之外。

### POC-012 — 僅在啟動時載入

**狀態：** 已接受（Accepted），適用於本 POC

NuGet 套件在使用端應用程式啟動時載入中央設定，並提供執行期間固定不變的快照。中央 `Set` 與移除操作的結果，只有在應用程式重新啟動後才會出現。

輪詢、推播通知、執行期間重新載入、最後已知良好狀態的持久化，以及自動更新，均已延後。本 POC 假設參與的應用程式可以在示範之間重新啟動。

### POC-013 — 設定來源的優先順序

**狀態：** 已接受（Accepted）

有效設定由低到高的優先順序如下：

1. `appsettings.json`
2. `appsettings.{HostEnvironment}.json`
3. 中央設定
4. 使用者祕密（User Secrets）
5. 環境變數
6. 命令列引數

較高優先順序的維運設定來源可以覆寫中央值。保留的 `CentralConfig:*` 命名空間中的啟動設定，本身不能由中央設定提供或覆寫，以避免啟動相依形成循環。

POC-037 將兩個設定鍵選擇陣列的支援宣告來源限縮為基底 `appsettings.json`。這個僅針對陣列的支援邊界，不改變上述有效應用程式值或其他本機啟動設定的一般優先順序。

POC-044 定義 .NET 8 主機配接器介面，以及將中央設定提供者（Provider）放在這個位置的支援機制。

### POC-014 — 在 appsettings.json 宣告設定鍵選擇

**狀態：** 已接受（Accepted）

在本 POC 中，使用端應用程式依 POC-037 定義的來源限制，在基底 `appsettings.json` 中宣告完整的設定鍵選擇。應用程式的啟動程式碼呼叫 POC-044 定義的單一註冊操作並等待完成；不會在程式碼中重複宣告相同的選取設定鍵。

這有利於示範清楚呈現、在存放庫中直接檢視，以及以重新啟動為基礎的操作方式。代價是宣告錯誤會在啟動時發現，而非編譯時。

### POC-015 — 混合程式碼與 appsettings 的宣告

**狀態：** 已延後（Deferred）

曾考慮一種混合介面，允許部分設定鍵選擇在程式碼宣告，其他部分在 appsettings 宣告。這可讓設定鍵與其 Options 型別放在一起，並改善重構，但也會產生兩個事實來源，需要合併、重複與優先順序規則。

**重新評估條件：** 設定鍵的所有權需要與 Options 註冊放在一起、編譯時可發現性比維運簡單性更重要，或 appsettings 宣告不一致已成為經證實的問題。

由於所有宣告來源都能正規化為相同的內部設定鍵選擇，重新評估此方案應不需要變更設定分發協定。

### POC-016 — 以兩個陣列作為對外宣告格式

**狀態：** 已接受（Accepted）

`CentralConfig` 區段提供兩個陣列：

- `CentralRequiredKeys`
- `FallbackAllowedKeys`

NuGet 套件在驗證與設定分發之前，將兩個陣列正規化為單一內部設定鍵選擇。這讓 POC 介面簡潔，同時在套件內保留單一處理路徑。

POC-036 定義每個宣告設定鍵的結構驗證，包括空白設定鍵與保留的 `CentralConfig` 根節點。依 POC-028，陣列內的重複與兩個陣列間的重疊，都以不區分大小寫的方式判定。依 POC-031，啟用中央設定時，合併後的設定鍵選擇必須至少包含一個設定鍵。POC-037 定義支援的宣告來源，以及呼叫端未遵守該限制時的 POC 行為。

### POC-017 — 物件陣列宣告格式

**狀態：** 已延後（Deferred）

曾考慮使用物件陣列，讓每個項目都包含 `Key` 與 `MissingBehavior`。對目前的兩種行為而言，此格式較冗長；但若引入第三種行為，或所有權、說明等逐鍵中繼資料，就會更適合。

### POC-018 — 設定分發回報設定值與缺少的設定鍵

**狀態：** 已接受（Accepted），適用於本 POC

成功的設定分發回應會區分回傳值與 `missingKeys`。批次要求不會只因個別設定鍵缺少就失敗；使用端應用程式套件會在取得完整回應後套用 POC-010。

空字串屬於回傳值，不得只因值為空就出現在 `missingKeys` 中。

### POC-019 — 在設定分發回應中明確提供 removedKeys

**狀態：** 已延後（Deferred）

### POC-020 — 兩個可執行主機與三個中央 HTTP 介面

**狀態：** 已接受（Accepted），適用於本 POC

本 POC 有兩個可執行主機，以及三個中央 HTTP 介面：

1. 中央設定主機擁有 SQLite，在同一個繫結上，提供使用不同位址的管理介面（Management interface）與設定分發介面（Distribution interface），以及一個維運就緒狀態介面。
2. 示範使用端主機（Demo Consumer Host）安裝 NuGet 套件，並在啟動時透過套件僅呼叫設定分發介面。

NuGet 套件是使用端應用程式內的程序內程式庫，不是第三個主機。未來的 .NET Framework 4.8 套件可透過穩定的設定分發 HTTP 契約實作相同的使用端角色，無須變更中央設定主機。

**修訂 — 2026-09-11：** POC-057 在相同中央程序與繫結上新增一個小型維運就緒狀態介面。兩個可執行主機與管理／設定分發架構仍為已接受；這項修訂並未完全取代本決策。

### POC-021 — 以 Controller 作為 HTTP 配接器

**狀態：** 已接受（Accepted），適用於本 POC

中央設定主機使用各自獨立的 ASP.NET Core Controller，作為管理介面與設定分發介面的 HTTP 配接器：

- 管理 Controller 提供建立 Set 與移除項目版本，以及查詢目前或歷史管理狀態的操作。
- 設定分發 Controller 提供 NuGet 套件使用的唯讀批次契約。

Controller 不互相呼叫，而是分別進入管理與設定分發模組；這兩個模組可以共用相同的設定項目持久化實作與 SQLite 資料庫。POC-057 的維運就緒狀態介面由小型端點對應負責，不由 Controller 負責。Controller 是 HTTP 接合邊界上的配接器，而非介面本身。

本 POC 不使用 Minimal API 路由群組或單一混合 Controller。端點形式定義於 POC-022，操作契約定義於 POC-025 至 POC-027。POC-050 定義設定值邊界，POC-051 定義共用的要求驗證責任，POC-052 定義共用的錯誤表示格式，POC-053 則不在 POC 加入額外的應用程式大小限制。

### POC-022 — 明確的 Set、Remove 與 Resolve 命令端點

**狀態：** 已接受（Accepted），適用於本 POC

管理 HTTP 介面使用各自獨立的 Set 與 Remove 命令端點，不使用通用的項目版本端點，也不採用 REST 風格的原地更新與刪除：

- `POST /api/v1/management/configurations/set`
- `POST /api/v1/management/configurations/remove`

Set 與 Remove 使用不同的要求契約，因此「帶有值的移除」等無效組合不會進入模組。兩種命令成功時都追加一個項目版本；都不執行原地更新或實體刪除。

管理讀取使用獨立位址：

- `GET /api/v1/management/configurations/current`
- `GET /api/v1/management/configurations/history`

設定分發 HTTP 介面提供一個唯讀批次操作：

- `POST /api/v1/distribution/configurations/resolve`

Resolve 使用 POST，讓中央環境與可能較長的設定鍵清單能放在要求主體中傳送，避免查詢字串限制。它不執行寫入。管理命令契約定義於 POC-025，設定分發契約定義於 POC-026，管理端目前狀態與歷史紀錄契約定義於 POC-027。POC-050 定義設定值邊界，POC-051 定義共用的要求驗證責任，POC-052 定義錯誤承載資料，POC-053 則定義 POC 對託管框架大小限制的依賴。版本配置定義於 POC-023，重複 Remove 的行為定義於 POC-024。

### POC-023 — 各設定項目獨立的單調遞增版本號碼

**狀態：** 已接受（Accepted），適用於本 POC

每個設定項目都有伺服器產生的獨立 64 位元整數版本序列，其範圍限定於一組中央環境與設定鍵。第一次成功的 Set 建立版本 1，之後每次成功的 Set 或 Remove 命令，都建立下一個整數版本。呼叫端不能提供或選擇版本。

每次成功的 Set 都建立一個版本，即使值與前一個值相同。成功的 Remove 也會依 POC-024 的嚴格狀態轉換建立版本。

最大版本號碼決定目前狀態。`CreatedAtUtc` 是稽核中繼資料，絕不決定排序。SQLite 內部可以使用另一個全域代理資料列 ID，但該 ID 不是管理介面對外提供的項目版本。

版本配置與插入必須是原子的，讓並行命令無法產生重複版本。POC-048 定義用來維護這項不變條件的 SQLite 寫入交易與可觀察順序，POC-049 定義等待耗盡後的 busy／lock 處理。設定分發回應仍只提供值與缺少的設定鍵；本 POC 的版本中繼資料僅限於管理命令與歷史紀錄回應。

### POC-024 — 嚴格的移除狀態轉換

**狀態：** 已接受（Accepted），適用於本 POC

移除是從中央值存在，轉換為沒有目前中央值的狀態。只有最新項目版本為 Set 時才會成功：

- 中央值存在的設定項目回傳 `201 Created`，並追加一個移除項目版本。
- 從未存在的設定項目回傳 `404 Not Found`，不追加任何內容。
- 最新項目版本已是移除的設定項目回傳 `409 Conflict`，不追加任何內容。

設定項目從未存在、目前存在或已移除時，Set 都仍有效，而且一律追加下一個項目版本。並行 Set 與 Remove 命令依 POC-048，在有序的寫入交易內針對最新狀態判斷此轉換，而非依 HTTP 到達時間。本 POC 不加入冪等鍵：若成功的 Remove 回應遺失，重試會得到 `409 Conflict`，操作人員可檢查目前狀態或歷史紀錄。未來可為自動化的正式環境管理用戶端重新考慮要求冪等性。

### POC-025 — 管理命令契約

**狀態：** 已接受（Accepted），適用於本 POC

`POST /api/v1/management/configurations/set` 接受一個包含 `environment`、`key` 與 `value` 的 JSON 物件。中央環境與設定鍵不得為空白。值為必要欄位且不能是 null，但空字串仍有效。

`POST /api/v1/management/configurations/remove` 接受只包含 `environment` 與 `key` 的 JSON 物件；此契約沒有值欄位。

成功的 Set 或 Remove 回傳 `201 Created`，並採用相同的中繼資料格式：`environment`、`key`、伺服器產生的 `version`、操作後的 `state`，以及伺服器產生的 `createdAtUtc`。Set 後的狀態為 `Present`，Remove 後為 `Removed`。Remove 錯誤依 POC-024 處理。

命令回應不回傳設定值。這避免將可能敏感的值不必要地複製到 Proxy、記錄與操作工具；需要明確取得值時，由管理端目前狀態查詢負責。設定鍵與中央環境的比對規則定義於 POC-028，POC-050 定義設定值大小限制，POC-051 定義要求驗證責任，POC-052 定義 Problem Details 錯誤承載資料，POC-053 則刻意不在 POC 加入其他由應用程式定義的大小限制。

### POC-026 — 最小化的設定分發批次契約

**狀態：** 已接受（Accepted），適用於本 POC

`POST /api/v1/distribution/configurations/resolve` 接受一個包含 `environment` 與 `keys` 的 JSON 物件。NuGet 套件傳送中央必要設定鍵與允許後備設定鍵的去重聯集。它不傳送使用端應用程式識別或缺值行為；這些責任保留在使用端內。

成功的回應回傳 `200 OK`，包含兩個欄位：

- `values`：將每個存在且已要求的設定鍵，對應到其字串值的 JSON 物件。
- `missingKeys`：包含沒有目前中央值之要求設定鍵的 JSON 陣列。

`values` 與 `missingKeys` 中的設定鍵必須互斥，且合起來恰好完整分割去重後的要求設定鍵。若回應包含未要求的設定鍵、某個要求設定鍵在兩個集合中都缺少、同一設定鍵重複出現在兩個集合，或回傳 null 值，該回應即無效，並使使用端啟動失敗。空字串值仍有效。

從未建立與已移除的設定鍵都出現在 `missingKeys` 中，它們的存在不會讓 HTTP 回應變成錯誤。NuGet 套件在取得完整回應後，套用本機的設定鍵選擇。設定分發回應不包含項目版本中繼資料、時間戳記、使用端資訊、缺值行為或 `removedKeys`。

包含逐鍵狀態的項目陣列回應已延後，因為 POC 沒有逐鍵回應中繼資料。值字典能更直接對應到 .NET 設定提供者，也讓跨框架的 HTTP 介面更精簡。

### POC-027 — 管理端目前狀態與歷史紀錄契約

**狀態：** 已接受（Accepted），適用於本 POC

`GET /api/v1/management/configurations/current` 使用必要的 `environment` 與 `key` 查詢參數。從未建立的設定鍵回傳 `404 Not Found`。已存在的設定項目回傳 `200 OK`，包含最新項目版本的 `environment`、`key`、`version`、`state`、`value` 與 `createdAtUtc`。

最新版本為 Set 時，`state` 為 `Present`，`value` 為非 null 字串；空字串仍是有效值。最新版本為 Remove 時，`state` 為 `Removed`，`value` 為 null。已移除的設定項目刻意回傳 `200 OK`，以區別從未存在的設定項目。

`GET /api/v1/management/configurations/history` 使用相同的必要查詢參數。從未建立的設定鍵回傳 `404 Not Found`。已存在的設定項目回傳 `environment`、`key`，以及依版本號碼遞減排序的 `versions` 陣列。每個項目包含 `version`、`operation`、`value` 與 `createdAtUtc`。Set 項目的操作為 `Set`，值為非 null，包含空字串；Remove 項目的操作為 `Remove`，值為 null。

本 POC 不將歷史紀錄分頁。這些管理回應會提供實際值，供明確的管理與診斷使用；由於 POC-040 刻意排除身分驗證、授權與傳輸安全設計，POC 必須使用非敏感示範值。POC-039 仍規範不洩漏設定值的診斷與記錄。依 POC-026，設定分發刻意不包含歷史紀錄。

### POC-028 — 不區分大小寫的設定項目識別與標準顯示拼寫

**狀態：** 已接受（Accepted），適用於本 POC

中央環境與設定鍵的識別都不區分大小寫；中央設定主機與 NuGet 套件全程採用序數不區分大小寫（ordinal case-insensitive）語意。例如，`(Development, Demo:Message)` 與 `(development, demo:message)` 識別同一個設定項目，因此共用同一個項目版本序列。僅改變大小寫絕不能建立不同的值。

第一次成功的 Set 決定該設定項目儲存的中央環境與設定鍵顯示拼寫。之後的管理命令與讀取可使用任意大小寫，會解析至同一個設定項目，並回傳已儲存的顯示拼寫。設定分發對已存在的設定項目使用儲存的拼寫；若要求的設定鍵從未存在，因此沒有儲存拼寫，`missingKeys` 就回傳要求中的拼寫。完整分割與重複檢查都不區分大小寫。

中央環境或設定鍵的前後空白為無效輸入，必須拒絕，不可悄悄修剪。設定鍵選擇驗證同樣將僅大小寫不同的宣告視為重複，並將 `CentralRequiredKeys` 與 `FallbackAllowedKeys` 中僅大小寫不同的成員視為重疊。

持久化透過具名稱的 SQLite 自訂定序強制執行識別規則，其比較委派給 `StringComparer.OrdinalIgnoreCase`。每個連線都必須在對結構描述執行陳述式前註冊該定序。識別欄位宣告相同定序，使唯一性限制與查詢條件使用領域定義的精確比對語意，同時保留原先插入的中央環境與設定鍵字串作為顯示拼寫。實作不得依賴 SQLite 預設比較、內建 `NOCASE` 定序，或透過 `ToUpperInvariant()` 產生的二進位識別。NuGet 套件在正規化設定鍵選擇與驗證回應時，直接使用 `StringComparer.OrdinalIgnoreCase`。

**修訂 — 2026-08-30：** 先前已接受的文字要求另外保存正規化的識別值。整合設計審查發現，不變文化特性的轉大寫與序數不區分大小寫，不保證具有相同的 Unicode 等價類別，因此正規化的二進位設定鍵可能產生錯誤碰撞。已接受的自訂定序實作修正了此持久化機制，而不改變產品識別規則或第一次 Set 決定顯示拼寫的行為。

### POC-029 — 明確的中央環境啟動設定

**狀態：** 已接受（Accepted），適用於本 POC

啟用中央設定時，使用端應用程式必須明確提供非空白的 `CentralConfig:Environment` 啟動設定值。NuGet 套件將解析出的值作為設定分發要求的 `environment` 傳送；不會推導、不會給預設值，也不會改用 .NET 主機環境（Host Environment）。

中央環境與主機環境刻意彼此獨立。例如，主機環境為 `Staging-RegionA` 的使用端應用程式，可以選擇中央環境 `Staging`。因此兩者不同不構成驗證錯誤。本 POC 接受維護這個明確對應的維運責任，因為參與的應用程式可能使用不同的主機環境命名慣例。

`CentralConfig:Environment` 只會在加入中央設定提供者之前，從本機啟動設定解析。它位於保留的 `CentralConfig:*` 命名空間，依 POC-013，絕不能被中央設定選取、提供或覆寫。啟用中央設定時，缺少、空白或前後含空白的值會在發出任何設定分發要求前使啟動失敗，與 POC-028 一致。POC-031 定義的明確僅本機模式不需要此設定。

POC-044 定義的 .NET 8 主機配接器負責讀取此設定，並將解析出的字串傳入套件的載入模組。未來的 .NET Framework 配接器可透過自己的設定機制讀取同一個邏輯設定。配接器的差異不改變中央 HTTP 介面。

本 POC 已否決直接從 `IHostEnvironment.EnvironmentName` 推導中央環境，以及以主機環境為預設值並允許選擇性覆寫。前者無法表示必要的名稱對應；後者會產生兩條選擇路徑，讓實際使用的中央環境較不明確。

### POC-030 — 僅使用基底位址的設定分發啟動設定

**狀態：** 已接受（Accepted），適用於本 POC

啟用中央設定時，使用端應用程式設定一個必要的 `CentralConfig:BaseAddress` 啟動設定值。不設定完整的設定分發端點，也不設定獨立的設定分發路徑。NuGet 套件擁有 POC-022 定義的版本化 `/api/v1/distribution/configurations/resolve` 路由，並將它與設定的基底位址（Base Address）組合。

這讓每個使用端應用程式的介面不必包含中央 HTTP 路由細節。路由變更透過相容的套件變更表示，無須把新路徑複製到每個使用端設定。基底位址本身仍屬於本機啟動設定，可由較高優先順序的本機來源依部署調整，且依 POC-013，不能由中央設定提供或覆寫。

啟用中央設定時，缺少或空白的基底位址會在發送設定分發要求前使啟動失敗。POC-031 定義的明確僅本機模式不需要此設定。POC-033 允許閘道路徑前綴，POC-034 定義 URI 驗證與結尾斜線正規化。POC-040 不在 POC 加入使用端認證資料設定。

本 POC 已否決可設定的完整 `DistributionEndpoint`，以及分開的 `BaseAddress` 與 `DistributionPath` 欄位，因為兩者都在尚未證實使用端需求時暴露 HTTP 路由細節。

### POC-031 — 透過 CentralConfig:Enabled 明確選擇僅使用本機設定的模式

**狀態：** 已接受（Accepted），適用於本 POC

使用端應用程式設定 POC-032 要求的布林啟動設定 `CentralConfig:Enabled`，讓開發人員能在尚未選取中央設定鍵前先註冊 NuGet 套件，也能為了測試而明確切回本機設定。

`Enabled` 為 false 時，套件註冊成功，不驗證 `BaseAddress`、`Environment` 或兩個設定鍵選擇陣列。套件不發出設定分發要求，也不加入中央設定提供者。因此，既有本機設定提供者依其一般優先順序決定所有有效值。變更此模式會在下一次應用程式啟動時生效，與 POC-012 一致。

`Enabled` 為 true 時，套件在發出要求前驗證 `BaseAddress`、`Environment` 與兩個宣告陣列。`CentralRequiredKeys` 與 `FallbackAllowedKeys` 不區分大小寫的聯集，必須至少包含一個設定鍵。無效的啟動設定會在網路存取前使啟動失敗。

`CentralConfig:Enabled` 是本機啟動設定，絕不能由中央設定提供或覆寫。設為 false 是操作人員或開發人員的明確選擇，不是已啟用的中央要求失敗時自動採取的後備方式。`Enabled` 為 true 時，中央傳輸、伺服器與無效回應等失敗仍依 POC-011 使啟動失敗。

已否決在沒有啟用設定的情況下，將空的設定鍵選擇視為隱含的不執行任何操作，因為拼錯或未部署的宣告可能悄悄停用中央載入。也已否決所有模式都必須至少有一個設定鍵，因為那會阻礙分階段註冊套件，以及要求的僅本機測試流程。

### POC-032 — 必須明確宣告是否啟用

**狀態：** 已接受（Accepted），適用於本 POC

使用端應用程式只要註冊 NuGet 套件，本機啟動設定就必須明確將 `CentralConfig:Enabled` 解析為有效布林值。若設定或整個區段缺少、為 null、空白，或無法解析為布林值，應用程式啟動就會失敗。套件不指定隱含預設值。

啟動設定驗證分兩個階段。首先，套件驗證 `Enabled` 已明確提供且有效。結果為 false 時，依 POC-031 執行僅本機行為，並停止啟動設定驗證。結果為 true 時，繼續在網路存取前驗證基底位址、中央環境與設定鍵選擇。

這讓啟用與停用都是刻意的選擇。尤其是意外遺漏正式環境的啟用設定時，不能悄悄讓應用程式繼續使用本機設定執行。已註冊套件但尚未選取中央設定鍵的使用端應用程式，必須明確將 `Enabled` 設為 false。

已否決將省略的設定預設為 false，因為這會讓遺漏的部署設定與刻意選擇的僅本機模式無法區分。

### POC-033 — 基底位址中的閘道路徑前綴

**狀態：** 已接受（Accepted），適用於本 POC

`CentralConfig:BaseAddress` 可包含反向 Proxy 對外提供中央設定主機時使用的路徑前綴。NuGet 套件必須保留此前綴，並在其下追加套件擁有的設定分發路由。

例如，基底位址為 `https://internal.example/config-center/`，套件擁有的路由為 `api/v1/distribution/configurations/resolve` 時，目標為 `https://internal.example/config-center/api/v1/distribution/configurations/resolve`。

路徑前綴表示部署位置，不是使用端可設定的設定分發路由。依 POC-030，使用端應用程式仍不能取代版本化路由，也不能將個別操作指向任意路徑。

已否決將基底位址限制為通訊協定配置（scheme）、主機資訊（authority）與選用連接埠，因為部署在以路徑為基礎的反向 Proxy 後方是支援情境。精確驗證與結尾斜線正規化定義於 POC-034。

### POC-034 — 基底位址的驗證與正規化

**狀態：** 已接受（Accepted），適用於本 POC

啟用中央設定時，`CentralConfig:BaseAddress` 必須能解析為帶有主機的絕對 HTTP 或 HTTPS URI。允許明確連接埠與閘道路徑前綴。查詢字串、片段，以及內嵌的使用者資訊，例如認證資料，均無效。無效的值會在網路存取前使啟動失敗。

設定的路徑可為空，也可有或沒有結尾 `/`。NuGet 套件將它正規化為恰好一個結尾斜線，再以不帶開頭斜線的相對路徑，追加套件擁有的 `api/v1/distribution/configurations/resolve` 路由。這會保留閘道前綴，並使 `https://gateway/config-center` 與 `https://gateway/config-center/` 成為等價輸入。

本 POC 允許本機與內部示範情境使用 HTTP，也接受 HTTPS 端點。POC-040 明確將強制 HTTPS、憑證原則與傳輸安全設計排除於 POC 之外；正式使用前必須重新評估這些議題。

已否決要求呼叫端提供結尾斜線，因為這個格式細節可能讓組合出的 URI 偏離最後一段前綴。也已否決接受查詢、片段、認證資料或任意 URI 配置，因為這些值不是中央設定主機位置的一部分，會讓要求組合方式模糊或不安全。

### POC-035 — 由使用端驗證不存在的後備值

**狀態：** 已接受（Accepted），適用於本 POC

設定分發將允許後備設定鍵回報於 `missingKeys` 時，NuGet 套件不為該設定鍵加入中央值，並繼續啟動。其他設定來源依 POC-013 正常參與。

若沒有任何設定來源提供該設定鍵，它會在有效設定中維持不存在，套件仍不會讓啟動失敗。使用端應用程式透過自己的設定或 Options 驗證，決定不存在是否有效。這讓某個允許後備設定鍵可以是選用的，另一個則必須由某處提供，而無須把這種應用程式專屬的差異加入套件介面。

中央必要設定鍵的行為不變：出現在 `missingKeys` 的中央必要設定鍵，無論其他來源是否提供值，都會使啟動失敗。中央系統故障也仍依 POC-011，對兩種行為都使啟動失敗。

已否決要求套件確認某處一定存在後備值，因為這會把「允許後備」重新定義為「應用程式必要」，使套件與使用端最終設定驗證耦合，也更難維持跨框架行為一致。也已否決為 POC 加入第三種缺值行為，因為既有的使用端驗證已負責此議題。

### POC-036 — 設定鍵的結構驗證

**狀態：** 已接受（Accepted），適用於本 POC

設定鍵必須是非 null、非空白，且前後不含空白的字串。它可為平面或階層式；`:` 是標準階層分隔符號，每個區段都不得為空白。開頭或結尾有分隔符號，以及空區段或只有空白的區段，例如 `:Demo`、`Demo:`、`Demo::Message` 或 `Demo: :Message`，均無效。

依 POC-028 的不區分大小寫識別規則，第一個區段不得等於 `CentralConfig`。這同時拒絕平面的 `CentralConfig` 設定鍵與所有 `CentralConfig:*` 子鍵，讓中央設定無法選取或覆寫自己的啟動設定命名空間。

除此之外，區段可包含 Unicode 與一般符號；本 POC 不套用僅允許 ASCII 的識別碼運算式。套件不會將宣告設定鍵中的 `__` 轉為 `:`。使用端應用程式必須宣告預期讀取的標準設定鍵。POC-053 刻意不在 POC 加入由應用程式定義的設定鍵總長度限制。

中央設定主機中的單一驗證模組，透過 POC-051 定義的手動 FluentValidation 邊界，對管理與設定分發輸入實作這些規則。NuGet 套件在網路存取前，對設定鍵選擇套用等價規則，不相依於 FluentValidation。這避免任何 HTTP 介面接受使用端配接器會以不同方式解讀的設定鍵。

已否決僅允許 ASCII 的運算式，因為它可能排除既有的 .NET 設定名稱，卻沒有為 POC 帶來價值。也已否決只拒絕整個空白字串的最低限度驗證，因為格式錯誤的階層設定鍵與保留的啟動設定命名空間會悄悄通過。

### POC-037 — 僅支援在基底檔案宣告設定鍵選擇

**狀態：** 已接受（Accepted），適用於本 POC

支援的使用端應用程式設定契約，要求 `CentralRequiredKeys` 與 `FallbackAllowedKeys` 都只宣告於基底 `appsettings.json`。主機環境專屬 JSON 檔案、使用者祕密、環境變數、命令列引數與其他較高優先順序的本機設定提供者，都不得在這兩個陣列下提供索引子項目。此限制只適用於設定鍵選擇陣列；`Enabled`、`BaseAddress` 與 `Environment` 仍使用已接受的本機設定提供者優先順序。

.NET 8 NuGet 套件取得的是 .NET 合併設定提供者後的有效本機 `IConfiguration`。在 POC 中，它會正規化並驗證最終設定鍵選擇，但不檢查設定提供者來源，也不證明陣列來自基底檔案。若較高優先順序的設定提供者提供了陣列索引，而合併後的選擇仍通過結構、重複、重疊與啟用驗證，套件可依 .NET 原生的索引層級合併繼續執行，不發出來源相關警告。此類宣告不在 POC 支援的契約內；不保證會使啟動失敗。

示範使用端主機只在基底 `appsettings.json` 中提供這兩個陣列。示範設定測試應維護這個範例慣例，但不宣稱能對任意使用端應用程式強制執行該規則。可辨識設定提供者的執行期間強制驗證，延後至考慮正式採用時，因為它會讓套件與使用端的設定管線耦合，且未來的 .NET Framework 配接器需要另做相容性工作。

若環境專屬的設定鍵選擇成為實際需求，或不受支援的陣列覆寫被證實有維運風險，則在正式推出前重新評估：可辨識來源的快速失敗驗證、專用宣告來源，或採用整個集合取代語意的對外格式。底層 .NET 行為與可用設計方式記錄於 [`.NET Configuration 的陣列與多 Provider 合併行為`](../knowledge/dotnet-configuration-array-merging.md)。

### POC-038 — 有上限的啟動重試與逾時策略

**狀態：** 已接受（Accepted），適用於本 POC

啟用中央設定時，一次設定分發載入最多執行一次初始 HTTP 嘗試與三次重試，合計最多四次嘗試。每次嘗試的逾時為五秒。重試延遲採指數退避，基準延遲依序為一、二、四秒；每次延遲各自加上獨立產生、介於零至 250 毫秒的隨機抖動。整個取得設定分發資料的過程，包含嘗試與重試延遲，總時間預算為 30 秒。成功時立即停止；總預算耗盡時，即使尚有可用嘗試次數，也使啟動失敗。

只有傳輸失敗、不是由呼叫端要求取消所引起的單次嘗試逾時，以及 HTTP `408`、`429`、`500`、`502`、`503` 與 `504` 才會重試。設定分發 Resolve 操作即使在 HTTP 配接器中使用 `POST`，仍可安全重試，因為該操作唯讀且沒有副作用。本 POC 使用套件擁有的退避時程，不允許伺服器提供的延遲延長 30 秒總預算。

無效的本機啟動設定會在網路存取前失敗。呼叫端要求的取消依 POC-047 立即停止操作，不重試。其他 HTTP 狀態碼，包括 `400`、`401`、`403` 與 `404`，語法上成功但內容無效或不可信賴的回應，以及缺少中央必要設定鍵的有效回應，都直接失敗，不重試。缺少允許後備設定鍵仍是成功的中央回應，並依已接受的本機後備行為處理。

重試次數、單次嘗試逾時、延遲、抖動範圍與總預算，都是由套件擁有的固定 POC 行為，不是新增的使用端應用程式設定。選用韌性程式庫或手動實作，屬於實作細節，只要維持此介面即可。斷路器、平行競速要求（hedging）、無上限重試、中央系統故障後自動使用本機後備值，以及逐使用端調整，都不在本 POC 策略範圍內。

### POC-039 — 具型別的啟動診斷與不洩漏設定值的記錄

**狀態：** 已接受（Accepted），適用於本 POC

NuGet 套件以單一公開的 `CentralConfigLoadException` 表示每個最終的中央啟動失敗，不以傳輸、逾時或反序列化例外作為主要介面。例外包含穩定的 `FailureKind`、嘗試次數、經過時間、選用的 HTTP 狀態碼、中央環境，以及診斷載入所需的其他安全背景資訊。失敗類型區分無效啟動設定、傳輸失敗、單次嘗試逾時、總逾時、未授權存取、其他 HTTP 失敗、無效回應，以及缺少中央必要設定鍵。只有在底層例外的完整診斷表示不會暴露禁止資料時，才可保留該例外。呼叫端要求的取消不屬於最終中央啟動失敗，依 POC-047 處理。

載入模組產生結構化診斷事件，不建立或設定自己的記錄提供者。.NET 8 主機配接器在使用端應用程式的 `ILogger` 管線可用時，將可用事件對應至該管線；缺少 Logger 絕不改變載入行為，POC-046 也將此不變條件延伸到提供的 Logger 同步擲出例外的情況。成功載入產生一則 Information 摘要，包含數量、嘗試次數與經過時間。每次排定重試產生一則 Warning，包含嘗試次數、安全的失敗分類、選用狀態碼與延遲。最終失敗時，若記錄可用，套件只嘗試發出一則由套件擁有的 Error，接著擲出 `CentralConfigLoadException`。套件不得嘗試發出該最終 Error 超過一次，但主機可能再記錄擲出的例外。接受這種可能重複的情況，因為套件不能假設每個主機都會記錄阻止主機建構的例外；遺失唯一的 Error 比重複記錄兩次更有害。

缺少的中央必要設定鍵名稱可出現在 `CentralConfigLoadException` 與套件擁有的最終 Error 事件中，因為這些名稱是修正宣告或中央資料所必需的。Information 層級不列出成功設定鍵名稱，也不列出缺少的允許後備設定鍵名稱；提供數量即可。可包含中央環境，以及已通過驗證、移除敏感資訊的端點。

來自中央或本機來源的設定值、連線字串、認證資料、授權標頭、權杖、Cookie、完整要求或回應主體、原始中央錯誤文字，以及任何未經審查、從回應內容衍生的剖析器訊息，絕不能進入例外、診斷事件或記錄。此限制透過不將禁止資料傳入診斷模型來強制執行，不依賴後續遮蔽程序。

正式的度量（Metrics）、分散式追蹤、穩定的量測工具名稱，以及 OpenTelemetry 相依性，都延後至 POC 之後。結構化啟動記錄與具型別的例外提供目前的診斷介面。若未來擴充可觀察性，設定鍵、端點位址、錯誤訊息，以及其他無界或敏感字串，不得成為度量標籤。

### POC-040 — 不驗證身分且僅供示範的安全邊界

**狀態：** 已接受（Accepted），適用於本 POC

本 POC 不實作身分驗證、授權、呼叫端身分、認證資料核發、API 金鑰或權杖處理，也不實作逐介面的權限策略。任何能連到中央設定主機的呼叫端，都能呼叫管理與設定分發 HTTP 介面。因此，使用端啟動設定除了已接受的基底位址之外，不加入認證資料設定，套件也不傳送身分驗證認證資料。

本 POC 不要求 TLS，也不定義憑證原則。由於管理讀取會提供設定值，管理命令又能變更這些值，中央設定主機不適合安全地用於正式環境，所有儲存值都必須是非敏感示範資料。它只能在預定的示範範圍內運作。

這項刻意排除的安全範圍不減弱 POC-039：設定值、認證資料、權杖與其他禁止資料，仍不得進入套件診斷或記錄。任何正式使用或儲存實際機密之前，必須先設計身分驗證、授權、傳輸安全、機密管理規則與介面專屬權限。

### POC-041 — 單一中央主機執行個體與單一 SQLite 檔案的拓撲

**狀態：** 已接受（Accepted），適用於本 POC

本 POC 恰好執行一個中央設定主機執行個體，由該程序恰好擁有一個本機 SQLite 資料庫檔案。同一個程序提供管理與設定分發 HTTP 介面。這就是 POC 單一來源拓撲的意義；與可能共同提供使用端應用程式有效設定的多個本機設定提供者無關。

本 POC 不支援多個中央設定主機執行個體、多個程序寫入同一個 SQLite 檔案、將資料庫檔案放在共用網路儲存體、複寫、容錯移轉、分割，或在多個資料庫檔案或中央來源之間選擇。

單一程序仍可能接收並行 HTTP 要求，因此依 POC-023，各設定項目的版本配置與插入仍必須是原子的。POC-048 定義可觀察的寫入順序與交易邊界。POC-049 定義 SQLite 日誌模式、有上限的 busy／lock 處理，以及對應的 HTTP 狀態。

### POC-042 — 以 Dapper 存取 SQLite 持久化資料

**狀態：** 已接受（Accepted），適用於本 POC

中央設定主機透過 Dapper 與 SQLite ADO.NET 提供者存取 SQLite。持久化使用明確 SQL，不引入 Entity Framework Core 或其變更追蹤。

Dapper 不定義資料庫結構描述、結構描述初始化或遷移機制，也不定義連線生命週期。POC-048 定義寫入交易邊界與並行命令順序，POC-049 定義日誌模式與 busy／lock 策略。Dapper 實作必須維持這些決策，以及 POC-007、POC-023、POC-024 與 POC-041 已接受的僅追加、版本配置、移除與單一檔案語意。

這項技術選擇保留於 POC 決策紀錄，不提升為 ADR，因為它只影響局部，若正式環境持久化設計改變，仍可逆轉。

### POC-043 — POC 保留每個項目版本

**狀態：** 已接受（Accepted），適用於本 POC

本 POC 在 SQLite 資料庫的存續期間，永久保留每個建立的項目版本。不執行到期、清理、封存、壓縮或實體刪除。移除仍追加一個移除項目版本，並保留所有較早的 Set 版本。

POC-027 接受的不分頁歷史紀錄回應，只適用於 POC 預期的示範資料量。正式使用或資料明顯成長之前，必須一併設計保留期間、封存或清理策略、歷史紀錄分頁、儲存限制與維運維護。

### POC-044 — 非同步 IHostApplicationBuilder 註冊與以錨點定位設定提供者

**狀態：** 已接受（Accepted），適用於本 POC

.NET 8 NuGet 套件提供以下基本的使用端應用程式註冊介面：

```csharp
public static Task AddCentralConfigAsync(
    this IHostApplicationBuilder builder,
    CancellationToken cancellationToken = default);
```

POC-045 加入呼叫端提供啟動 Logger 的多載，不改變此操作的載入順序或設定提供者放置位置。

使用端應用程式在 `WebApplication.CreateBuilder(args)` 或 `Host.CreateApplicationBuilder(args)` 之後、`Build()` 之前，恰好呼叫此操作一次，並等待完成。`WebApplicationBuilder` 與 `HostApplicationBuilder` 都符合 `IHostApplicationBuilder`，因此同一介面同時支援 POC 示範 API 與 .NET 8 Generic Host 應用程式，無須提供另一個僅供 Web 使用的註冊方式。未來的 .NET Framework 4.8 主機配接器可以提供適合該框架的介面，同時維持設定分發契約與載入語意。

此操作從 builder 上已存在的本機設定管線讀取啟動設定。中央設定停用時，依 POC-031 不存取網路，也不插入設定提供者。啟用時，先驗證啟動設定、完成設定分發資料取得、驗證缺值行為與回應，再插入不可變的啟動快照（startup snapshot）設定提供者。該設定提供者在同步 `Load` 操作中不執行網路 I/O，也不支援重新載入。

針對支援的 .NET 8 管線，主機配接器找出 `appsettings.{HostEnvironment}.json` 唯一的標準 JSON 來源，並緊接其後插入中央快照來源。這會產生 POC-013 接受的優先順序：基底 JSON、主機環境 JSON、中央設定、使用者祕密、環境變數與命令列引數。配接器不得將中央設定追加在末尾，因為那會錯誤地讓它優先於維運設定來源。

自訂設定提供者保留其與插入位置的實際關係：位於中央來源之前的既有來源優先順序較低，位於其後的既有來源優先順序較高，在 `AddCentralConfigAsync` 之後追加的來源也有較高優先順序。套件不重新排序或分類自訂設定提供者。若主機配接器無法識別唯一且無歧義的環境 JSON 錨點，就透過套件具型別的失敗介面使啟動失敗，不猜測位置，也不悄悄改變優先順序。

本 POC 不提供同步註冊多載、公開的設定提供者索引、`ConfigurationManager` 多載、公開的傳輸配接器，或用來變更路由、重試策略、設定鍵選擇或放置位置的選項委派。這些做法會將套件擁有的行為移到每個使用端應用程式，削弱單行宣告式介面。套件的接合邊界後方仍可有內部 HTTP 與記憶體內測試配接器，但不會成為使用端設定選項。

此決策確立呼叫端提供的取消權杖何時進入載入模組。POC-045 定義使用端應用程式如何選擇在 `Build()` 前接收診斷，POC-046 隔離該 Logger 的例外，POC-047 定義呼叫端要求的取消語意。

在示範使用端主機實際使用此介面，並證實相容性成本之前，此項仍維持為 POC 決策，不提升為 ADR。

### POC-045 — 呼叫端提供啟動 Logger 的多載

**狀態：** 已接受（Accepted），適用於本 POC

除了 POC-044 的基本註冊介面外，.NET 8 NuGet 套件提供以下多載：

```csharp
public static Task AddCentralConfigAsync(
    this IHostApplicationBuilder builder,
    ILogger startupLogger,
    CancellationToken cancellationToken = default);
```

使用端應用程式選擇恰好一個多載，作為唯一一次等待完成的註冊呼叫。`startupLogger` 引數為必要引數，且由呼叫端擁有。呼叫端可使用 `LoggerFactory.Create` 明確建立它，或傳入由外部組合根、測試基礎設施或啟動機制擁有的 `ILogger`。套件不擁有，也不釋放該 Logger。

使用此多載時，套件可在主機建構完成前，立即傳遞 POC-039 定義且不洩漏設定值的 `Information`、重試 `Warning` 與單一最終 `Error` 事件。不含 Logger 的多載仍是簡單的註冊路徑，不保證 `Build()` 前傳遞記錄或之後重播；中央啟動最終失敗時，`CentralConfigLoadException` 仍是呼叫端可觀察的診斷介面。

套件不建立或設定記錄提供者、不建立自己的 `LoggerFactory`、不建構暫時服務提供者，也不隱藏地以寫入 `Console` 作為後備。提供者選擇、篩選、輸出、生命週期與持久化，仍是呼叫端的責任。這可避免第二個容器，也防止套件繞過使用端應用程式的記錄策略。

已否決可為 null 的 Logger 參數、設定記錄的選項委派，以及由套件建立的預設 Logger。明確多載讓呼叫位置能直接看出有意選擇啟用，同時保留最小基本呼叫，並讓記錄基礎設施的所有權留在套件外。可重複使用的模式與範例記錄於 [呼叫端提供的啟動 Logger](../knowledge/caller-supplied-startup-logger.md)。

POC-046 定義提供的 `ILogger` 擲出例外時的行為。POC-047 另外定義呼叫端要求的取消，使這兩種行為都不會隱含在多載本身。

### POC-046 — 隔離呼叫端提供的啟動 Logger 例外

**狀態：** 已接受（Accepted），適用於本 POC

呼叫呼叫端提供的啟動 Logger，是盡力而為的診斷嘗試，不參與設定載入的控制流程。單一內部安全發送接合邊界，隔離每個從套件擁有的 `ILogger` 呼叫逸出的可攔截同步例外，包含使用 `IsEnabled` 時的例外。該邊界只包住記錄呼叫，不攔截設定取得、驗證、設定提供者插入，或建構不洩漏設定值的診斷模型所產生的例外。

`Information` 發送失敗不改變成功的載入或設定提供者插入。重試 `Warning` 失敗不改變重試時程、嘗試次數、逾時預算或最終結果。中央最終失敗時，套件先建立 `CentralConfigLoadException`，透過安全發送邊界嘗試發出最終 `Error` 一次，接著即使記錄失敗，也擲出同一個例外。呼叫端要求的取消也仍維持 POC-047 定義的取消結果，不會被 Logger 例外取代。

套件不重試失敗的記錄嘗試、不透過同一個 Logger 遞迴回報該失敗、不將它加入公開例外契約、不建立後備提供者，也不寫入 `Console`。同步 `ILogger` 呼叫返回後才發生的非同步提供者失敗，不在套件能觀察或隔離的範圍內。因此，POC 的單一最終 Error 規則表示一次發送嘗試，不保證持久化。

已否決傳遞 Logger 例外，因為那會讓選用診斷成為額外的啟動相依：`Information` 失敗可能將成功載入變成失敗呼叫，`Warning` 失敗可能繞過 POC-038 的重試，`Error` 失敗可能遮蔽 POC-039 要求的具型別例外。安全發送模式與其取捨記錄於 [呼叫端提供的啟動 Logger](../knowledge/caller-supplied-startup-logger.md)。

### POC-047 — 傳遞呼叫端要求的取消

**狀態：** 已接受（Accepted），適用於本 POC

呼叫端要求的取消是協作式控制流程，不是最終中央啟動失敗。`AddCentralConfigAsync` 因提供的 `CancellationToken` 已取消而停止時，回傳的 `Task` 以 Canceled 狀態完成，等待它會擲出與該呼叫端權杖相關聯的 `OperationCanceledException`。這同樣適用於基本註冊介面與呼叫端提供啟動 Logger 的多載。

呼叫端取消會停止目前嘗試或重試延遲、不再排定重試、不產生套件擁有的最終 `Error`，也不包裝成 `CentralConfigLoadException`。因此，使用端應用程式可使用標準 .NET 取消處理，獨立於套件具型別的中央失敗介面。

套件擁有的逾時仍是中央啟動失敗。分類取消時，若原始呼叫端權杖已被要求取消，則呼叫端取消優先於同時觀察到的單次嘗試逾時或總預算權杖。否則，總預算對應到 `CentralConfigLoadException`，失敗類型為 `TotalTimeout`；單次嘗試逾時依 POC-038 重試規則處理，成為最終失敗時對應到 `AttemptTimeout`。在較晚取消要求之前已完成的套件失敗，不會事後改成取消。

實作必須使用原始呼叫端權杖與套件逾時權杖的狀態來分類取消，不能只依賴執行階段例外型別，也不能要求連結權杖產生的例外必須包含原始權杖。當所有自有權杖都未被要求取消時，非預期的下游 `OperationCanceledException` 如何對應，仍屬詳細錯誤對應設計的一部分；不得將它誤報為呼叫端取消。

已否決將呼叫端取消包裝成 `CentralConfigLoadException`，因為這會讓 Task 從 Canceled 變成 Faulted，繞過一般取消攔截路徑與接續工作，並讓預期的關閉行為看起來像中央系統故障。雖然包裝可提供單一套件例外型別與額外診斷欄位，使用端仍須依失敗類型分支，避免錯誤的錯誤記錄、警示或重試。

### POC-048 — 以 SQLite 寫入交易決定管理命令的順序

**狀態：** 已接受（Accepted），適用於本 POC

每個管理 Set 或 Remove 命令，都在單一明確的 SQLite `BEGIN IMMEDIATE` 寫入交易內執行依狀態決定的工作。交易成功開始後，命令讀取該中央環境與設定鍵的最新項目版本、驗證要求的轉換、配置下一個逐項目版本、插入新的不可變項目版本，然後提交。提交前的失敗會回復交易，不追加項目版本，也不耗用版本號碼。

SQLite 成功取得寫入交易的順序，決定並行管理命令的序列順序。本 POC 不保證 HTTP 到達、進入 Controller、工作排程或回應完成的順序決定此序列。只有已提交交易可被觀察：設定分發或管理讀取可看見提交前或提交後的狀態，但絕不會看見部分套用的命令。

對同一設定項目的兩個並行 Set 都可成功，並依交易順序取得連續版本。並行 Set 與 Remove 命令各自依較早已提交交易留下的狀態評估 POC-024，因此最終狀態遵循同一順序。對中央值存在項目的兩個並行 Remove，結果是一個成功移除，接著一個 `409 Conflict`。不同設定項目的命令，也會暫時以寫入者身分序列化執行，因為 POC 接受 SQLite 單一寫入者限制。

已否決應用程式層級的全域 FIFO 佇列，因為它會增加佇列所有權、取消、關閉與復原行為，仍需要資料庫交易，而且只保護這個主機程序。也已否決使用呼叫端提供預期版本的樂觀並行控制，因為目前管理介面面向操作人員，沒有 `expectedVersion`，也不要求用戶端解決一般並行寫入。

POC-049 定義 SQLite 日誌模式、取得交易時的等待、重試責任，以及 `SQLITE_BUSY` 與 `SQLITE_LOCKED` 等待耗盡時的 HTTP 狀態對應。

### POC-049 — WAL 模式與有上限的 SQLite 競爭處理

**狀態：** 已接受（Accepted），適用於本 POC

中央設定主機在資料庫初始化時，以 `journal_mode=WAL` 明確啟用 SQLite 預寫式記錄，並驗證 SQLite 回報的有效模式為 `wal`。無法建立 WAL 模式時，主機啟動失敗。本 POC 使用 SQLite 自動檢查點行為，不加入手動檢查點排程器或調校介面。

WAL 模式讓設定分發與管理讀取者可與寫入者並行，同時保留 POC-048 接受的 SQLite 單一寫入者限制。額外的 `-wal` 與 `-shm` 輔助檔案，是使用中本機資料庫的預期組成部分，不是獨立設定來源，也不是應用程式會在主機執行期間刪除的檔案。

每個開啟的 SQLite 連線都使用 `Microsoft.Data.Sqlite`，並設定 `Default Timeout=5`。提供者在回傳 Busy 或 Locked 最終結果前，可套用此共用的有限等待；它不提供獨立等待策略，讓應用程式等待 Busy 同時強制 Locked 立即返回。應用程式不對任何一種結果額外重試或退避。這能避免一般短暫競爭立即失敗，又不會在提供者之上疊加第二個重試預算。

若 SQLite 在提供者等待後回傳最終 `SQLITE_BUSY`，包含延伸 busy 結果，受影響的管理或設定分發操作回傳 `503 Service Unavailable`，採用 `persistence_busy` Problem Details 契約。若 SQLite 在提供者等待後回傳最終 `SQLITE_LOCKED` 或延伸 locked 結果，操作不執行應用程式重試，記錄伺服器端 `Error` 事件，並回傳 `500 Internal Server Error`，採用 `persistence_failure` Problem Details 契約，因為同一連線或共用快取衝突被視為非預期的持久化實作失敗，而非一般寫入者競爭。兩種結果都不對應到 POC-024 表示設定項目已移除的領域層級 `409 Conflict`。維運就緒狀態則回傳 POC-057 定義的安全彙總 `503`。

HTTP 回應不提供原始 SQLite 例外、資料庫路徑、連線字串、SQL 文字或設定值。POC-052 定義共用的 Problem Details 格式、穩定錯誤碼、安全回應欄位，以及此回應不傳送 `Retry-After` 標頭的決策（該回應狀態為 `503`）。

已否決預設的回復日誌模式，因為管理寫入可能不必要地阻擋設定分發讀取。已否決沒有 busy 逾時便立即失敗，因為短暫重疊的管理命令會太容易失敗。也已否決應用程式層級的指數重試，因為 SQLite busy 處理器已執行有限等待，第二套策略會延長並複雜化要求預算。

**修訂 — 2026-08-30：** 先前已接受的文字暗示可對 Busy 設定提供者層級的等待，而讓 Locked 立即返回。整合設計審查確認，`Microsoft.Data.Sqlite` 提供一個共用命令／交易逾時，而非獨立的 Busy 與 Locked 等待控制。最終 HTTP 對應與不採用應用程式層級重試的決策不變；只修正對提供者控制能力的假設。

### POC-050 — 設定值的最大 UTF-8 大小

**狀態：** 已接受（Accepted），適用於本 POC

設定值以 UTF-8 編碼時，最多可包含 16 KiB，即 16,384 位元組。限制包含上限值。空字串仍有效，佔用零個 UTF-8 位元組。

限制適用於 JSON 反序列化後的語意字串，不是 `.NET String.Length`、JSON 跳脫表示，或完整 HTTP 要求的大小。共用驗證實作以 `Encoding.UTF8.GetByteCount(value)` 計算。管理 Set 的值超過上限時，視為無效輸入，依 POC-052 的 Problem Details 契約回傳 `400 Bad Request`。設定分發不得回傳超過同一契約上限的值，NuGet 套件也將此類回應視為無效中央回應，不載入該值。

這是設定分發應用程式策略，不宣稱是資料庫連線字串或 ADO.NET 提供者的通用上限。一般連線字串預期能在上限內保有充足餘裕。此邊界仍可防止單一純量設定項目變成無界文件或二進位容器，並限制其要求、回應、記憶體、SQLite 與永久保留項目版本的成本。大型文件、憑證承載資料與二進位內容，不屬於本 POC 的設定值模型。

實作必須以具名稱常數只宣告此邊界一次，例如 `MaxConfigurationValueUtf8Bytes = 16 * 1024`；不得在不同呼叫位置重複寫入字面值 `16384`。常數宣告必須附上簡短理由註解並引用 `POC-050`，讓後續維護者能區分刻意的資源邊界與提供者專屬的魔術數字。邊界測試必須涵蓋恰好 16,384 UTF-8 位元組、16,385 位元組、多位元組字元與空字串。

POC-053 刻意不在 POC 加入由應用程式定義的最大 HTTP 要求主體、中央環境或設定鍵長度、Resolve 設定鍵數量、設定鍵位元組總數，或設定分發回應總大小。設定值上限仍是唯一 POC 專屬的位元組大小邊界。

### POC-051 — 在中央 HTTP 邊界手動執行 FluentValidation

**狀態：** 已接受（Accepted），適用於本 POC

.NET 8 中央設定主機使用 FluentValidation 12，對成功反序列化的管理與設定分發要求 DTO 執行語意驗證。驗證器透過相依性注入註冊為 `IValidator<TRequest>`。每個 Controller 動作在進入管理或設定分發模組前，都明確等待 `ValidateAsync` 完成；POC 不使用 MVC 自動驗證，也不使用不受支援的 `FluentValidation.AspNetCore` 整合套件。

驗證器集中處理 POC-025、POC-026、POC-028、POC-036 與 POC-050 已接受的要求規則。POC-053 不為這些驗證器新增其他由應用程式定義的大小規則。各獨立欄位持續驗證，使單一回應能回報所有可獨立偵測的輸入錯誤。同一欄位的相依規則鏈中，一旦 `NotNull` 或 `NotEmpty` 等前置條件失敗，就停止驗證，避免重複失敗，或對 null 值計算 UTF-8 大小等不安全的後續檢查。

在 FluentValidation 執行前，ASP.NET Core 與 System.Text.Json 仍負責傳輸表示格式：缺少主體、JSON 格式錯誤、不相容的 JSON 權杖型別，或未對應的 JSON 屬性，都回傳 `400 Bad Request`。未對應屬性必須禁止，而非悄悄忽略，使拼錯的屬性與傳送到 Remove 契約的 `value` 成員不能在未被發現的情況下通過。無法反序列化的要求，不會另外產生語意驗證失敗，因為沒有可信賴的 DTO 可供驗證。

成功反序列化後，任何 FluentValidation 失敗同樣回傳 `400 Bad Request`，且不會執行管理或設定分發模組，也不執行持久化操作。驗證器回傳穩定、由中央主機擁有的錯誤碼、安全欄位路徑與固定訊息，不回傳設定值或其他不可信輸入。POC-052 定義 Problem Details 格式，並將傳輸與語意驗證失敗都對應至該格式。

驗證錯誤仍與領域及基礎設施結果分開。有效 Remove 指向從未存在的設定項目時，回傳 `404 Not Found`；指向已移除設定項目時，回傳 `409 Conflict`；有效 Resolve 中缺少的設定鍵仍是成功的 `200 OK`；SQLite 失敗維持 POC-049 定義的對應。FluentValidation 不查詢資料庫，也不作為以例外驅動的控制流程。

使用端 NuGet 套件不參考 FluentValidation，也不在公開介面提供 FluentValidation 型別。它透過套件內部驗證執行少量啟動設定與設定鍵選擇檢查，同時維持 POC-028 與 POC-036 要求的等價語意。這讓公開套件的相依性介面維持精簡，並避免未來的 .NET Framework 4.8 Receiver 與最低支援執行階段為 .NET 8 的 FluentValidation 12 耦合。

驗證器測試將每個驗證器視為黑箱，涵蓋有效要求、各自無效的欄位、相依規則短路、不區分大小寫的重複設定鍵、設定鍵結構失敗，以及 UTF-8 值邊界。HTTP 整合測試另外涵蓋 JSON 格式錯誤、不相容權杖型別、未知屬性、`400` 對應，以及無效要求不會進入模組或持久化操作的保證。

### POC-052 — RFC 9457 Problem Details 錯誤契約

**狀態：** 已接受（Accepted），適用於本 POC

對每個已定義的管理或設定分發操作，在選定端點後、回應開始前產生的錯誤回應，均使用 RFC 9457 Problem Details 格式與 `application/problem+json` 媒體類型。這包含選定操作的語意驗證失敗，以及 ASP.NET Core 或 System.Text.Json 傳輸驗證失敗。實作透過 ASP.NET Core 的 Problem Details 服務，或等價的單一錯誤對應元件，集中對應錯誤，不在個別 Controller 建立互不相關的承載資料。`GET /health/ready` 使用 POC-057 的安全彙總 JSON 回應，不使用 Problem Details。

本 POC 刻意讓每個 Problem Details 回應都使用 `"type": "about:blank"`，因為尚未提供穩定的文件來源來說明自訂問題型別。`title` 是 HTTP 狀態的標準原因片語，數值 `status` 成員一律等於實際回應狀態。`detail` 是固定、安全、供人閱讀的英文訊息，不是機器可讀契約。`instance` 只包含要求路徑，不包含查詢字串。

此契約涵蓋的每個 Problem Details 回應，都包含兩個擴充成員：`code` 是由中央主機擁有、穩定的 snake_case 機器辨識碼；`traceId` 則是用來尋找對應伺服器端記錄的關聯識別碼。用戶端依 HTTP 狀態與 `code` 分支，不剖析 `title`、`detail` 或驗證訊息。未來若從 `about:blank` 改為有文件說明的自訂型別 URI，需要協調契約版本更新，不能悄悄改變本 POC 契約的意義。

只有 `validation_failed` 包含 `errors` 成員。它是平面陣列，元素格式為 `{ "path": string, "code": string, "message": string }`。`path` 與 `code` 是穩定且安全的識別碼，`message` 是固定的說明訊息。陣列順序不屬於契約。FluentValidation 失敗使用驗證器擁有的欄位路徑與錯誤碼。傳輸驗證失敗使用以下對應：

| 條件 | 錯誤路徑 | 錯誤碼 |
| --- | --- | --- |
| 缺少要求主體 | `$` | `body_required` |
| JSON 格式錯誤 | `$` | `invalid_json` |
| 不相容的 JSON 權杖型別 | 安全的 JSON 路徑 | `invalid_type` |
| 未對應的 JSON 屬性 | `$` | `unknown_property` |

傳輸錯誤對應不回傳未知成員名稱、格式錯誤的輸入或原始剖析器訊息。共用傳輸主體讀取器，比對選定要求 DTO 允許的頂層成員與收到的物件，以分類 `unknown_property`；不剖析依實作而異的 `JsonException.Message` 文字。這刻意犧牲部分用戶端細節，換取 POC-039 接受的穩定且不洩漏設定值的診斷邊界。

語意驗證回應的代表格式如下：

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "One or more request fields are invalid.",
  "instance": "/api/v1/management/configurations/set",
  "code": "validation_failed",
  "traceId": "00-...",
  "errors": [
    {
      "path": "environment",
      "code": "required",
      "message": "Environment is required."
    },
    {
      "path": "key",
      "code": "invalid_configuration_key",
      "message": "Configuration Key has an invalid structure."
    }
  ]
}
```

中央主機對已知失敗使用以下頂層對應：

| HTTP 狀態 | Problem `code` | 意義 |
| --- | --- | --- |
| `400 Bad Request` | `validation_failed` | 傳輸或語意要求驗證失敗。 |
| `404 Not Found` | `configuration_not_found` | 要求的設定項目從未存在。 |
| `409 Conflict` | `configuration_already_removed` | Remove 指向目前狀態已為 Removed 的設定項目。 |
| `503 Service Unavailable` | `persistence_busy` | SQLite 在 POC-049 的有限等待後仍忙碌。 |
| `500 Internal Server Error` | `persistence_failure` | SQLite 回傳 locked 結果，或其他已知的持久化實作失敗。 |
| `500 Internal Server Error` | `internal_error` | 發生非預期的應用程式失敗。 |

依 POC-018，有效 Resolve 中缺少的設定鍵仍屬於成功的 `200 OK` 回應，不是 Problem Details。本 POC 的 `persistence_busy` 回應不包含 `Retry-After` 標頭：中央主機無法預測鎖定剩餘時間，任意延遲會成為沒有根據的魔術數字，而使用端 NuGet 套件已擁有 POC-038 固定且有限的啟動重試策略。

Problem Details 絕不提供設定值、要求或回應主體、原始 SQLite 或 JSON 剖析器錯誤、SQL 文字、資料庫路徑、連線字串、堆疊追蹤、查詢字串，或未經審查的例外訊息。固定的 `500` 說明不揭露實作細節；完整例外細節只限伺服器端記錄，透過 `traceId` 關聯，並受 POC-039 不洩漏設定值的記錄規則與 POC-040 不驗證身分的示範邊界約束。

只有要求選定已定義的中央主機 API 操作，且回應尚未開始時，才保證此格式。未匹配的路由、不支援的 HTTP 方法、Kestrel、反向 Proxy 或其他傳輸層，可能在操作能建立承載資料之前，產生或拒絕契約外的回應。若在回應標頭或主體序列化開始後發生失敗，就無法可靠地將回應改寫為 Problem Details；主機會中止該回應，並在伺服器端診斷保留失敗。本 POC 因此不宣稱每個路由、網路或回應串流失敗都有相同表示格式。

契約測試涵蓋媒體類型、必要成員、HTTP 狀態與 `status` 成員相等、各已知狀態／錯誤碼對應、驗證錯誤格式、陣列順序不屬於契約、追蹤關聯、遮蔽規則，以及 `Retry-After` 不出現在 `persistence_busy` 回應。測試也區分選定操作的錯誤與路由、Proxy 或傳輸拒絕，避免宣稱契約邊界外的保證。

**修訂 — 2026-08-30：** 先前已接受的文字未指定穩定的未知要求屬性偵測機制，也未說明 HTTP 回應開始後的邊界。整合設計審查明確補上這兩項限制，不改變 RFC 9457 回應格式或既有的狀態／錯誤碼對應。

**修訂 — 2026-10-21：** 初始實作把 POC-039 用戶端套件「不將禁止資料傳入診斷模型」的作法套用到中央主機，伺服器端日誌完全不記錄例外，維護人員因此無法從 `traceId` 追到根本原因。本修訂明確定義伺服器端界線：中央主機的 Error 日誌記錄完整例外（訊息、堆疊追蹤與內層例外）；防止設定值進入日誌的責任放在來源，中央主機自己的例外訊息必須是固定文字，並由慣例測試守護；要求主體與查詢字串仍不寫入日誌。理由是中央主機的日誌只屬於單一服務、由其維運團隊管理，與會進入每個使用端日誌管線的用戶端套件不同；事後遮蔽無法可靠辨識任意訊息中的設定值，因此不採用。HTTP 回應契約不變：Problem Details 仍不包含任何例外資訊。POC-039 對用戶端套件的規則維持不變。若未來中央要保存機密，日誌界線不足以保護機密，需另行決定機密的保存與標記方式。

### POC-053 — POC 不額外加入由應用程式定義的大小限制

**狀態：** 已接受（Accepted），適用於本 POC

除了 POC-050 的 16 KiB 設定值邊界外，本 POC 不為中央環境長度、設定鍵長度、Resolve 設定鍵數量、設定鍵位元組總數、完整 HTTP 要求主體大小，或設定分發回應總大小，定義由應用程式擁有的數值上限。中央設定主機不覆寫主控框架的要求大小設定，使用端 NuGet 套件也不引入獨立的設定分發回應大小上限。

這不表示系統沒有上限。Kestrel、反向 Proxy、System.Text.Json、HttpClient、SQLite 與可用程序記憶體，仍各自有實作與部署限制。這些限制可能依主控拓撲或框架版本而異，不提升為設定分發 HTTP 或 NuGet 套件契約的一部分。若要求在選定操作產生回應之前，就被 Kestrel 或 Proxy 拒絕，仍不在 POC-052 的 Problem Details 保證內；因此 POC 不定義由應用程式擁有的 `request_too_large` Problem 錯誤碼。

本 POC 保留其他決策已接受的語意規則：依 POC-025 與 POC-028，中央環境與設定鍵仍為必要，且須遵守空白規則；設定鍵保留 POC-036 的結構與保留根節點驗證；設定鍵選擇保留重複、重疊、啟用與結構檢查；每個設定值仍受 POC-050 限制。本決策只移除 POC-050 之後考慮過的額外數值大小與批次上限。

此範圍是刻意的，因為 POC 旨在示範集中管理設定值，以及「使用端應用程式 → NuGet 套件 → 中央設定主機」流程。尚未量測代表性應用程式就選定維運上限，會產生任意限制，可能在尚未掌握專案實際設定清單前，就拒絕合法專案。本 POC 接受主控堆疊允許的承載資料，可能消耗比正式部署允許的更多 CPU、記憶體、查詢工作或啟動時間。

若未來評估正式環境採用，維護者必須盤點代表性應用程式，並至少量測中央環境與設定鍵長度、每個應用程式選取的設定鍵數量、設定鍵位元組總數、序列化後的 Resolve 要求與回應大小、設定值大小分布、使用端啟動記憶體與時間，以及實際閘道與主控拓撲施加的限制。任何正式環境上限與安全餘裕，都必須根據這些證據制定，並附上相容性、負載與邊界測試，不可直接複製框架預設值或未經量測的 POC 設定。

本 POC 不針對 Kestrel、Proxy、HttpClient、System.Text.Json 或 SQLite 的數值預設限制建立測試斷言，因為它們不是應用程式契約。測試仍涵蓋 POC-050 的設定值邊界與所有非大小相關的語意驗證規則。相關框架行為，以及它們與應用程式自有契約的區別，記錄於 [HTTP、ASP.NET Core 8、System.Text.Json 與 HttpClient 的大小限制筆記](../knowledge/dotnet-http-size-limits.md)。

### POC-055 — 示範主機的限定範圍與根層級有效設定端點

**狀態：** 已接受（Accepted），適用於本 POC

示範使用端主機針對最終有效的 `IConfiguration`，提供兩個不驗證身分的唯讀 HTTP 介面：

- `GET /api/v1/demo/effective-configuration` 是優先使用的示範介面。它只列舉固定 `Demo:*` 區段下的設定值，並回傳相對於 `Demo:` 的路徑。
- `GET /api/v1/demo/unsafe/root-configuration` 是明確標示不安全的診斷介面。它從根層級列舉設定值，因此可能回傳本機 JSON 設定、中央值、啟動設定、使用者祕密、環境變數、命令列值、連線字串，或程序可取得的其他任何值。

這兩個介面都在 NuGet 套件依 POC-013 與 POC-044 放置設定提供者之後，讀取使用端應用程式的最終設定。不呼叫中央設定主機、不提供套件下載的回應，也不推導哪個設定提供者提供值。輸出只示範合併後的有效結果。依 POC-012，中央變更在示範使用端主機重新啟動前仍不可見；較高優先順序的本機設定提供者則仍可能決定顯示的有效值。

優先使用介面的回應格式如下：

```json
{
  "scope": "Demo",
  "effectiveValues": {
    "CentralRequiredMessage": "central-value",
    "FallbackAllowedMessage": "local-fallback",
    "Features:0": "FeatureA"
  }
}
```

不安全回應使用 `"scope": "Root"`，包含固定警告 `"This response may expose sensitive configuration values."`，並在同一個 `effectiveValues` 物件回傳相對於根層級的設定鍵。階層路徑仍以 `:` 攤平成字串，使輸出符合 .NET 設定鍵語意。空字串保留為實際值。只用於分組子鍵的 null 區段節點會省略，JSON 屬性順序不屬於契約。

成功呼叫任一介面，都回傳 `200 OK` 與 `application/json` 媒體類型。若選定範圍沒有非 null 設定值，`effectiveValues` 是空 JSON 物件；沒有值不構成 HTTP 錯誤。

兩種回應都使用 `Cache-Control: no-store`。兩個介面都不記錄回傳的設定鍵或值，也不回傳設定提供者來源或中央項目版本中繼資料。示範使用端主機與程序可取得的所有值，都必須維持在 POC-040 要求的非敏感示範範圍內。

不安全介面一律對應路由。本 POC 刻意不加入 `EnableUnsafeRootConfigurationEndpoint` 設定、身分驗證規則、自動遮蔽、主機環境限制，或其他執行期間防護。是否呼叫它，由示範操作人員負責。`unsafe` 路由區段、固定回應警告與文件用來傳達已接受的風險，不會讓介面變安全，也不會讓它適合正式使用。

測試驗證：優先使用介面不能列舉 `Demo:*` 之外的值；不安全介面無須啟用設定，就能列舉該區段外的有效值；兩者都保留空字串與設定提供者優先順序；都不回報來源；都傳送 `Cache-Control: no-store`。

- `appSettings`、`connectionStrings`、自訂區段、本機後備、啟動設定，以及設定提供者或區段的優先順序，如何對應到已接受的產品語意；
- 各主機在哪裡執行啟動載入，以及受控的同步邊界、逾時、取消、啟動失敗與早期記錄如何運作；
- 套件要採獨立的 `net48` 配接器、共用且與框架無關的核心，或多目標 Receiver，以及支援哪些 `packages.config`、`PackageReference`、相依性、繫結重新導向、部署與 CI 矩陣。

此決策未選定任何候選整合路徑。為避免重複技術調查，已驗證的 Framework 行為、候選方式、套件取捨、代表性應用程式盤點與後續探索問題，保留於 [.NET Framework 4.8 Receiver 相容性知識筆記](../knowledge/dotnet-framework-48-receiver-compatibility.md)。

**重新評估條件：** .NET 8 示範審查要求加入 Framework 第二階段。選出三至五個代表性舊版應用程式，依其實際設定存取、主機生命週期、套件管理、相依性與部署特性，選擇第一個支援範圍。

### POC-057 — 最小化的中央就緒狀態介面與啟動識別值

**狀態：** 已接受（Accepted），適用於本 POC

中央設定主機提供一個未版本化的維運介面：
GET /health/ready。只有帶有 ready 標籤的 SQLite 檢查能在
共用的五秒資料庫逾時內開啟設定的資料庫，並驗證
第 1 版結構描述時，才回傳 200。已完成的 Degraded 或 Unhealthy 報告
回傳 503。兩種回應都使用 application/json、Cache-Control: no-store，且
恰好只包含 status 與 instanceId；絕不提供健康檢查項目、持久化
細節、設定資料、例外或堆疊追蹤。

中央主機從 CentralHealth:InstanceId 擷取一個啟動範圍的識別值
（環境設定中為 CentralHealth__InstanceId）。設定缺少時，
產生一個 N 格式的小寫 GUID。若有設定但值不符合標準格式，
則在主機開始接聽前使啟動失敗。此值在該程序中不可變。

啟動識別值是關聯證據，不是機密、認證資料、授權
權杖或密碼學的程序證明。E2E 在每個已清理的子程序環境中提供新的識別值，
且只接受識別值相符的回應作為就緒狀態證據。
接著另外驗證管理介面的 404 configuration_not_found 契約，
作為獨立的業務介面證據。不同但有效的識別值，證明
該位址由另一個接聽者擁有；格式錯誤的回應仍屬契約
失敗，不會轉成位址重試。

不新增存活狀態或啟動路由。POC 也不加入身分驗證、
TLS、專用管理連接埠、健康狀態發布器、詳細健康報告、
部署資訊清單、監控策略或自動重新啟動策略。

### POC-058 — 列出中央環境設定鍵的管理介面

**狀態：** 已接受（Accepted），適用於本 POC

**日期：** 2026-10-21

管理介面原本只能依單一設定鍵查詢目前狀態與歷程，無法回答「某個中央環境目前有哪些設定」。示範時觀眾很可能提出這個問題，日常管理也需要它。新增 `GET /api/v1/management/configurations?environment=...`，契約定義於設計文件第 4.5 節。

取捨如下：

- **不回傳設定值。** 列表用來概覽，值仍透過 `current` 依設定鍵取得。這讓回應大小只隨設定鍵數量成長，也避免一次揭露整個環境的值。
- **包含已移除的項目。** 依 POC-007 與 POC-008，移除是附加的版本，項目仍存在；列出 Removed 狀態能讓管理者看出該設定鍵曾經存在，並接著查詢歷程。只列出 Present 項目會讓清單與 `current`、`history` 的結果不一致。
- **不分頁。** 依 POC-053，POC 不定義數量限制。單一示範環境的設定鍵數量很小；若正式環境需要分頁，再隨正式持久化選型（POC-054）一併決定。
- **空環境回傳空陣列。** 中央不登記中央環境，也不登記使用端（POC-003）；沒有項目的環境與從未使用的環境無法區分，兩者都是 `200 OK`。

此介面與其他管理介面一樣不驗證身分（POC-040），只用於隔離環境的非敏感資料。它不改變 Resolve 的契約，也不讓中央得知哪些使用端讀取了哪些設定鍵。
