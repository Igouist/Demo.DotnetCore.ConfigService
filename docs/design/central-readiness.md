# 中央就緒狀態探針與啟動識別值設計

> **審查狀態：** 已核准（Approved）2026-09-11
>
> **方向核准日期：** 2026-09-10
>
> **目標：** 維運就緒狀態與啟動關聯契約

## 1. 決策

中央設定主機將提供一個精簡的維運探針：`GET /health/ready`。

回應將包含一個不可變、限定於該次啟動的 `instanceId`。E2E 測試框架會為每次中央設定主機啟動提供全新的預期 ID，且只有在回應包含完全相同的 ID 時，才接受其就緒狀態。

這會取代目前以兩秒程序穩定性推斷就緒狀態的方式。當框架擁有的中央子程序仍在初始化、尚未嘗試繫結其連接埠時，這可防止契約相容的外部接聽程序滿足就緒條件。

這項變更刻意在管理介面與設定分發介面之外，新增中央設定主機的第三個 HTTP 介面。它仍是隔離 POC 的維運介面，不是身分驗證或強化正式環境安全性的功能。

## 2. HTTP 契約

探針使用位於 `/api/v1` 之外、不含版本的維運路由。

`GET /health/ready` 回傳 `200 OK` 的必要條件，是具時限的唯讀操作能開啟已設定的 SQLite 資料庫，並驗證其第 1 版結構描述。所有已完成的 `Degraded` 或 `Unhealthy` 結果都對應至 `503 Service Unavailable`；若呼叫端中止要求，要求可能在未回應的情況下結束。

`200` 與 `503` 回應都只有一個 `application/json` Content-Type 值、一個原始 `Cache-Control: no-store` 值，且最上層成員恰好如下：

```json
{
  "status": "ready",
  "instanceId": "794c1ca58c1342a6863d81e152777b17"
}
```

就緒狀態探針成功時，`status` 為 `ready`；失敗時則為 `unavailable`。不可用的回應仍包含相同的 `instanceId`，讓呼叫端能區分自己的尚未就緒執行個體與其他接聽程序。

屬性順序不屬於契約。回應絕不包含中央環境、設定鍵、設定值、資料庫路徑、連線字串、SQL 文字、健康檢查細節、堆疊追蹤或例外訊息。

不新增存活狀態（liveness）或啟動路由。目前 POC 沒有使用存活狀態的使用端，也沒有應用程式自行擁有的存活狀態。SQLite 初始化也會在 `app.RunAsync` 之前完成，因此 HTTP 啟動路由無法觀察啟動中的中間狀態：啟動前無法連線至該位址，啟動後就緒狀態路由即已可用。需要啟動探針的協調器可使用適合啟動階段的失敗容許額度呼叫 `/health/ready`。正式環境的存活狀態政策需要另行設計部署方式，且不得將依賴 SQLite 的就緒狀態結果重用為自動重新啟動的訊號。

## 3. 啟動識別值

主機設定鍵為 `CentralHealth:InstanceId`；其環境變數形式為 `CentralHealth__InstanceId`。

識別值遵循下列規則：

1. 若未提供此設定，主機會在程序啟動時產生一個全新的 GUID。
2. 若提供此設定，值必須是 32 個小寫十六進位字元，表示 `N` 格式的 GUID。
3. 無效的設定值會讓啟動在伺服器開始接聽之前失敗。錯誤內容固定，且不會回顯遭拒的值。
4. 標準化後的值只擷取一次，不會因設定重新載入而變更。
5. 同一程序的每個回應都包含相同的值。

E2E 測試框架會為每次啟動嘗試產生新值，包括位址重試與保留原位址的重新啟動。它只透過既有、已清除無關與敏感項目的子程序環境傳遞該值，不透過命令列，也不修改程序全域環境。

此識別值是關聯值，不是秘密、認證資料、授權權杖或密碼學上的程序證明。它可讓測試框架避免誤認過期或意外出現的相容接聽程序。可檢查其他程序環境或蓄意冒充其他程序的惡意程序，仍不在此未驗證身分的 POC 威脅模型範圍內。

## 4. 中央設定主機的實作結構

健康檢查行為封裝在一個精簡的對應介面後方。既有的 `AddCentralConfigHost` 註冊負責必要服務，而 `Program.cs` 只新增 `MapCentralHostReadinessProbe()`。

實作在 `CentralHost/Health` 下包含三個內部型別：

- `CentralHostInstanceIdentity` 解析或產生不可變的識別值；
- `SqliteReadinessHealthCheck` 將持久化層的就緒狀態轉接至 ASP.NET Core Health Checks；以及
- `CentralHostReadinessEndpoint` 負責路由對應、狀態對應、安全的 JSON 輸出及快取標頭。

`SqliteDatabaseInitializer` 新增一個內部就緒狀態操作，重用既有的第 1 版相容性檢查與連線清理路徑。它會將取消訊號傳遞至每個 SQLite 操作。Health Check 註冊與 SQLite 連線共用既有的五秒資料庫逾時值，因此整個檢查只有一個由伺服器掌控的期限，而非無時限或另行設計的額度。健康檢查轉接器將成功對應至 `Healthy`，一般相依性失敗則一律對應至 `Unhealthy`；呼叫端取消仍維持取消語意。端點僅將 `Healthy` 對應至 `200`，並將 `Degraded` 與 `Unhealthy` 都對應至 `503`。

就緒狀態註冊包含一個標記為 `ready` 的檢查，端點判斷式只執行具有該標記的檢查。持久化細節保留在持久化實作內；不引入新的公開儲存庫介面、假的儲存抽象、結構描述變更或寫入探針。

ASP.NET Core Web 共用架構已提供 Health Checks。此設計不新增套件相依性。

## 5. E2E 就緒狀態流程

`PocProcessEnvironment` 保留目前的呼叫端介面：情境繼續呼叫 `StartCentralAsync` 與 `RestartCentralAsync`，無須處理識別值。

每次內部啟動時，測試框架會：

1. 產生預期的執行個體 ID；
2. 將它加入僅供子程序使用的環境；
3. 啟動並登錄框架擁有的 `ChildProcess`；
4. 使用既有的單次要求一秒逾時與整體啟動 15 秒期限輪詢 `/health/ready`，每次要求都與框架擁有的程序結束訊號競速；以及
5. 只有在探針回傳 `200`、精確且各只有一個值的媒體類型與 `no-store` 標頭、`status == "ready"`，以及完全相符的預期 ID 時，才接受探針結果。

輪詢結果如下：

| 觀察結果 | 意義與處理方式 |
| --- | --- |
| 子程序仍存活時發生連線失敗或要求逾時 | 啟動可能仍在進行；在期限內繼續。 |
| 符合精確 `503` 契約且具有預期 ID | 框架擁有的子程序已可連線但尚未就緒；在期限內繼續。 |
| `200`、預期 ID 與精確契約皆符合 | 已確認框架擁有的程序就緒。 |
| 符合精確契約，但具有另一個有效 ID | 外部或過期的接聽程序占用該位址；依下述外部接聽程序轉移流程處理。 |
| 契約缺失、格式錯誤或其他無效情形 | 以無效就緒狀態回應判定此次啟動失敗；不得以位址重試掩蓋可能的產品缺陷。 |
| 框架擁有的子程序結束 | 在時限內讀取完所有輸出，再回報已分類的啟動失敗。 |
| 整體期限到期 | 不等待尚未完成的輸出分類，直接回報啟動逾時，再執行既有的具時限清理。 |

確認框架擁有的程序就緒後，測試框架保留既有管理介面的 `404 application/problem+json` 回應，並要求 `code == "configuration_not_found"`，作為獨立的業務介面證據。探針、管理介面證據與最後一次自有程序結束檢查，都共用原本的 15 秒期限。每個 HTTP 操作都與 `process.WaitForExitSignalAsync()` 競速。只有通過最後的結束檢查後，才可將端點公布給後續操作。管理介面回應不再用於確認程序身分。

符合精確契約但具有另一個有效 ID 的回應，是其他接聽程序占用回送位址的直接證據；此分支不等待位址已占用的輸出標記。它先透過具時限清理終止此次啟動的子程序。若是中央設定主機的初次啟動，接著選取新保留的連接埠、產生新 ID，並在既有的五次嘗試上限內重試。保留原位址的重新啟動不得變更連接埠，因此清理後會產生既有的位址已占用重新啟動失敗。格式錯誤的回應仍是已完成的契約失敗，絕不轉成位址重試。

移除中央設定主機固定兩秒的穩定性觀察窗口。

## 6. 位址已占用的觀察與清理

獨立的位址已占用回歸問題也必須修正；只有識別值探針，無法修正其假設兩秒內完成的問題。

若位址衝突未回傳有效的外部識別值，位址已占用偵測會在自有程序的 stdout 與 stderr 輸出到達時，即時觀察既有框架的例外標記，而不等程序結束及兩個輸出讀取工作都完成後才檢查緩衝輸出。比對仍採不區分大小寫的序數比較（ordinal-ignore-case），並使用目前的允許清單：`AddressInUseException`、`address already in use` 及 Windows 通訊端位址錯誤用語。偵測使用啟動期限的剩餘時間，不另行假設兩秒內完成。

辨識到輸出標記可提早將啟動失敗分類，但不會放寬程序所有權的清理要求：終止與處置仍須透過既有的具時限終止路徑，讓框架擁有的程序停止，並讓兩個輸出讀取工作都完成。啟動逾時不再負責進一步排空輸出；完整讀取剩餘輸出的責任仍屬於程序終止流程與 `Dispose`。

這將兩項責任分開：

- 輸出觀察決定啟動失敗的原因；以及
- 程序完成決定何時能安全釋放資源。

固定等待時間不會成為正確性的證據。

## 8. 驗證

實作採先寫測試的開發方式。驗收要求如下：

- 已設定且符合標準格式的識別值原樣回傳；
- 未提供識別值時產生一個值，且在程序生命週期內維持不變；
- 無效識別值在開始接聽前安全地失敗；
- SQLite 可用時就緒狀態回傳 `200`，具時限的相依性檢查失敗時回傳 `503`；
- 就緒狀態只執行有標記的 SQLite 檢查、傳遞取消訊號，並將 `Degraded` 或 `Unhealthy` 對應至 `503`；
- 所有探針回應都符合精確的單一原始標頭值、媒體類型、成員、狀態與 no-store 契約；
- 任何回應或失敗診斷都不揭露持久化或設定資料；
- 中央設定主機每次重試與重新啟動都收到全新的預期識別值；
- 拒絕契約相容但具有不同識別值的外部接聽程序；
- 無須固定的穩定性等待，即可偵測位址已占用輸出；
- 共用期限的最終所有權關卡，只有在框架擁有的程序仍存活時才成功，且啟動逾時不等待尚未完成的輸出分類；以及
- 程序結束及兩個輸出讀取工作仍須在處置前完成；以及
- 聚焦測試、所有 E2E 測試、完整方案測試、Release 建置、格式驗證與 `git diff --check` 均通過。

## 9. 明確排除的目標

這項變更不新增：

- 存活狀態或啟動路由，或背景啟動狀態機；
- 身分驗證、授權、TLS 或專用管理連接埠；
- 執行個體識別值的安全保證；
- 詳細健康報告、相依性名稱、例外輸出、度量或健康狀態發布器；
- 新的持久化抽象、寫入探針或結構描述遷移；
- 用戶端或示範使用端主機探針；
- 容器資訊清單或部署政策；或
- 既有 E2E 生命週期規則之外的自動重試。
